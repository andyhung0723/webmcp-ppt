AGENT READINESS FRAMEWORK

Cloudflare 拆解的四個面向

— 01
Discoverability
找得到
  • —robots.txt 宣告哪些 bot 能爬、哪些路徑禁止
  • —sitemap.xml 網站地圖，一次列出所有重要頁面
  • —Link headers (RFC 8288) 在 HTTP 回應標頭直接指向相關資源
先有 robots.txt 與 sitemap，告訴 agent 從哪裡進來；用 Link headers 在回應裡直接指路，別讓它自己亂猜。
— 02
Content
讀得懂
  • —Markdown for Agents 透過內容協商回傳乾淨 Markdown，而非人類用的複雜 HTML
提供乾淨文字版，少讓 agent 拆複雜 HTML；內容有結構、有脈絡，才不會讀錯重點。
— 03
Bot Access Control
管得住
  • —Content Signals 宣告內容可被 AI 搜尋／不可訓練等用途
  • —robots.txt AI bot 規則 針對 AI 爬蟲設定可否存取
  • —Web Bot Auth 用密碼學簽章驗證 bot 身分，不只看 User-Agent
說清楚哪些 bot 可以看，哪些地方不能進；最好能驗證身份，而不是只靠 User-Agent。
— 04 ← 今天的重點
Capabilities
知道你能做什麼
  • —Agent Skills 可呼叫的技能清單
  • —API Catalog (RFC 9727) 機器可讀的 API 目錄
  • —OAuth/OIDC discovery (RFC 8414/9728) 自動找到授權端點
  • —MCP Server Card MCP server 能力名片
  • →WebMCP 在網頁裡直接宣告可呼叫的能力
把可執行的事列出來：查詢、建立草稿、送出申請；WebMCP 就是在網頁裡宣告這些能力。

Implementation · WebMCP API
10 / 19
TWO WAYS TO REGISTER TOOLS

WebMCP 怎麼寫

IMPERATIVE API · DOCUMENT.MODELCONTEXT

用 JS 在 runtime 註冊 tool，掌控度最高。 

document.modelContext.registerTool({
  name: 'prepare_leave_request',
  description: '建立一張請假申請草稿',
  inputSchema: {
    type: 'object',
    properties: { startDate, endDate, reason },
    required: ['startDate', 'endDate'],
  },
  execute: async input =>
    leaveRequestActions.prepareDraft(input),
});
inputSchema= 告知 agent 此 tool 需要的參數
execute= agent 呼叫這個 tool 時，實際要做的事
DECLARATIVE API · HTML 屬性

既有 HTML form 加上 toolname / tooldescription 屬性就能宣告成 tool——不寫 JS 的最低成本路徑。 

<form toolname="prepare_leave_request"
      tooldescription="建立一張請假申請草稿">
  <input name="startDate" type="date" required>
  <input name="endDate" type="date" required>
  <textarea name="reason"></textarea>
  <button type="submit">送出</button>
</form>
自動推導input 的 name／type／required → 直接變 inputSchema
一表單兩用同一張表單，人能送、agent 也能呼叫，共用同一套檢查

Architecture · Tool Design
15 / 19
DON'T WRAP THE DOM

不要把 Tool 寫成 DOM 腳本

✗  01 · BAD
包一層 DOM click 
execute: () => {
  document.querySelector(
    '.btn-submit'
  )?.click();
};
本質還是 UI automation，UI 一改照樣壞。
✓  02 · BETTER
寫入 form state
execute: async input => {
  leaveFormStore.patch(input);
  await validateLeaveRequest(
    input
  );
};
不依賴 selector，走既有驗證，錯誤講得出是哪個欄位。
✓  03 · BEST
接 domain action
execute: async input =>
  leaveRequestActions
    .prepareDraft(input);
UI 改版不碎 contract；UI 與 Agent 共用同一套 business behavior；權限稽核集中、可測試。
Design Principles · WebMCP Tools
16 / 19
GOOD TOOLS ≠ EXPOSE EVERYTHING

設計 WebMCP Tool 的六個原則

01
Schema 要穩定
不跟 UI component 綁死。Angular 改 Vue、按鈕搬位置，capability 不應跟著碎。
02
表達 intent，不是 click
不要 clickBuyButton，要 addToCart、prepareCheckout——Agent 要的是產品語意。
03
破壞性動作拆兩段
付款、取消、刪除：先 preview 建 draft 回給使用者確認，再走 confirm。
04
回傳結果可解釋
失敗不要只回 false——說為什麼、缺什麼、下一步能做什麼，Agent 才能修正。
05
權限稽核產品化
權限、rate limit、audit log 是產品的一部分。WebMCP 是另一個入口，不是後門。
06
Tool 也要被測試
Tool 跟 service 一樣要單測：餵 input 斷言回傳、驗錯誤訊息夠不夠 Agent 自我修正。

Reality Check · Limits & Risks
18 / 19
NOT PRODUCTION-BLIND YET

限制與風險

— 01 / SPEC
規格成熟度

還在 Origin Trial（Chrome 149 起，本機開 flag 就能測）。API 還會變——光是 navigator 搬到 document 就改過一次，得一路盯著。

— 02 / SECURITY
安全性

你開出來的每個 tool，都是新的攻擊面——prompt injection、被惡意頁面騙著呼叫。權限、稽核這些不會自己長出來，得自己設計。

— 03 / EVAL
可靠性

Agent 會不會傳錯參數？出錯時你的訊息夠不夠它自己修回來？每個 tool 上線前都要先測過。

測試工具 ↑ Google I/O 2026 同場也端出給 agent 用的 Chrome DevTools——chrome-devtools-mcp 的 list_webmcp_tools / execute_webmcp_tool 已經能找出並呼叫頁面上註冊的 WebMCP tool（實驗性 · Chrome 149+），正好拿來自動跑 eval。
